# Transactional Outbox для событий Kafka

Статус: принято

## Контекст

События (`BatchStarted`, `BatchReleased`, `BatchQuarantined` и др.) публиковались в Kafka внутри
транзакции БД. Это dual-write: при откате транзакции событие уже ушло (фантом), при недоступности
Kafka данные сохранены, а событие потеряно.

## Решение

Событие записывается в таблицу `outbox_events` в той же транзакции, что и бизнес-данные.
`OutboxRelay` по расписанию читает неотправленные записи (`FOR UPDATE SKIP LOCKED`, несколько
экземпляров приложения не отправят событие дважды), отправляет в Kafka, ждёт подтверждения и
помечает `sent_at`. Порядок сохраняется: при ошибке пакет прерывается. В конверт события входят
`eventId`, `type`, `schemaVersion`, `occurredAt`, `data`.

## Последствия

- Нет фантомных и потерянных событий; доставка «как минимум один раз».
- Потребитель обязан быть идемпотентным по `eventId`.
- Появляется задержка доставки (интервал опроса) и таблица, которую нужно чистить по сроку хранения.
- Для одного небольшого завода Kafka может быть избыточной; outbox позволяет заменить транспорт (например, на вебхуки) без изменения бизнес-кода.
